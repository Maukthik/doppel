Run it on a pull request

Any public PR to a Python web app. Doppel replies on a GitHub issue in 1 to 5 minutes, with a link to the check page.

Opens a GitHub issue with the link filled in. Submit it to start the run.

What happens when you submit

  1. The issue starts a workflow in doppel-try, a public repo you can read.
  2. It checks out the commit the PR started from and the PR's latest commit.
  3. Both go to Nebius sandboxes, where the app is installed and its own tests run: twice on the old code, once on the new.
  4. Nemotron judges every difference against the PR's description, and Doppel replies on the issue.

Works when the tests run from tox.ini, a CI workflow, a Makefile or a noxfile (Flask, Django, FastAPI). If Doppel can't compare the two versions, the reply says why; it never says “no regressions”. Runs are public and capped per day, because each one uses real sandboxes.

Three runs, two comparisons

A test suite checks what someone thought to assert. Doppel records everything the app answers, so a field nobody asserts on still shows up.

base

The code the PR started from. Every request and response is recorded.

base again

The same code, run a second time. Whatever differs from the first run is noise (timestamps, tokens, random IDs) and is ignored.

head

The code with the PR. Every other difference is a change in behavior. It is re-checked by running the tests involved again, then Nemotron labels it intended, regression or needs a human, using the PR's description, never the diff alone.

Test mode, on this page

The users are the app's own tests, recorded request by request. No setup: the commands come from the repo. The tests run from the base branch, so a PR can't edit a test to hide a change.

The guided twin, in the GitHub Action

Nemotron 3 Ultra lists the regressions it suspects; Nemotron writes users and probes that send the exact inputs. Each suspicion ends confirmed, refuted or untested. It needs a doppel.toml, which doppel init writes.
